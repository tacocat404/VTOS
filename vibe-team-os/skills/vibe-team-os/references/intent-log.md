## 무엇을 남기는가

대화의 대부분은 결정이 아니다. 결정에만 로그를 남긴다.

| 로그가 됨 | 로그가 안 됨 |
|---|---|
| 되돌리기 어려운 선택 | 오타 수정, 문구 다듬기 |
| 다른 팀원에게 영향이 감 | 혼자 시도하고 버린 것 |
| PRD 에 반영될 것 | 이미 정한 것의 단순 실행 |
| 방향을 바꾸는 것 | "이거 어때?" 수준의 탐색 |

**체크포인트당 0~3건이 정상이다.** 5건이 넘으면 기준이 느슨한 것이다.
**0건인 구간도 정상이다.** 하루 종일 조사만 했으면 결정이 없을 수 있다. 억지로 만들지 않는다.

대화를 통째로 남기면 양이 많아 아무도 안 읽는다. 그러면 기록이 있으나 마나가 된다.

---

## 파일 형식

`members/<이름>/logs/LOG-0001.md`

```markdown
---
id: LOG-0012
author: hong
date: 2026-09-03T14:32:00+09:00
status: 결정됨
confidence: confirmed
links: [PRD-3.2]
topic: 로그인
files: [src/auth.js]
---

# 소셜 로그인 단일 단계로 통합

## 요청
> "로그인 화면 좀 더 간단하게 만들어줘"

## 의도 분석
표면 요청 · 로그인 UI 단순화
실제 목적 · 첫 진입 이탈률을 낮추려는 것
근거 · 직전 대화에서 "가입하다 다 나가는 것 같다"고 언급

## 확인 질문
Q. 단순화의 기준은? 입력 필드 수 / 단계 수 / 시각 요소?
A. 단계 수. 3단계를 1단계로.

## 결정
소셜 로그인 단일 단계로 통합. 이메일 가입은 보조 경로로 내림.

## 남은 질문
- 기존 이메일 가입자는 어떻게 옮기나?
```

## 머리말 필드

| 필드 | 필수 | 형식 | 설명 |
|---|---|---|---|
| `id` | ✅ | `LOG-0001` (숫자 4자리 이상) | 팀원 폴더 안에서 고유 |
| `author` | ✅ | 폴더 이름 (`hong`) | 누가 남겼나 |
| `date` | ✅ | `2026-09-03` 또는 시각까지 | 언제 |
| `status` | ✅ | `논의중` `결정됨` `보류` `폐기` | 아래 「상태 바꾸기」 |
| `confidence` | | `confirmed` `unconfirmed` | 의도의 근거가 있나 |
| `links` | | `[PRD-3.2]` | 반영될 목차 항목 |
| `orphan` | | `true` | 목차에 없는 아이디어 — 오류가 아니다 |
| `supersedes` | | `[LOG-0016]` | 이 결정이 밀어낸 이전 로그 |
| `topic` | | `로그인` | **검색 키.** 목차 밖 아이디어 묶기에도 쓴다 |
| `files` | | `[src/auth.js]` | **검색 키.** Phase 2 겹침 판정에도 쓴다 |

## 본문 항목

**반드시 있어야 하는 것 셋**

| 항목 | 내용 |
|---|---|
| `# 제목` | 한 줄 요약. **머리말 바로 다음.** 목록과 카드에 이게 그대로 실린다 |
| `## 요청` | 사용자가 실제로 한 말. **그대로 인용한다** |
| `## 의도 분석` | 표면 요청 / 실제 목적 / 근거 |
| `## 결정` | 무엇으로 정했나 |

**필요할 때 덧붙이는 것**

| 항목 | 언제 |
|---|---|
| `## 확인 질문` | 되물었을 때 |
| `## 남은 질문` | 답을 못 찾은 게 있을 때 — 대시보드에 모인다 |
| `## 왜 다른 안을 안 골랐나` | 병합에서 한쪽을 골랐을 때 |

**제목은 60자 안으로.** 없으면 빌더가 「결정」 첫 줄을 잘라 쓰는데, 그러면 목록에서
제목과 요약이 같은 문장으로 두 번 나오고 마크다운 기호까지 딸려 온다.

`## 요청`에 사용자 말을 그대로 넣는 이유는, **나중에 의도 분석이 의심스러울 때 원문과 대조하기 위해서**다. 요약하면 대조가 불가능해진다.

## 의도 분석 — 근거가 없으면 빈칸

**이 항목 하나가 이 제품의 신뢰를 결정한다.**

```
표면 요청 · 사용자가 말한 것 그대로
실제 목적 · 왜 그걸 원하는가
근거 · 그렇게 판단한 이유 (사용자 발언 인용)
```

구분자는 `·` 를 쓴다. `:` 나 `-` 도 인식되지만 하나로 통일한다.

### 지어내지 않는다

```
사용자: "로그인 화면 좀 더 간단하게 만들어줘"
```

여기서 **"첫 진입 이탈률을 낮추려는 것"은 어디서 나왔는가?** 사용자는 이탈률을 한 번도 말하지 않았다. 그럴듯해서 쓴 것이다.

진짜 이유는 "어제 본 앱이 예뻐서"일 수도 있다. **사용자 본인도 자기 의도를 모를 때가 많다.**

더 나쁜 건 그다음이다.

```
지어낸 의도 → 영구 보존 → PRD 근거 → 발표물 "내가 인식한 문제"
```

**본인이 하지도 않은 생각이 발표 자료에 실린다.** 심사위원이 "이탈률 데이터 있나요?" 물으면 대답을 못 한다.

### 근거가 없을 때 쓰는 법

```markdown
## 의도 분석
표면 요청 · 로그인 UI 단순화
실제 목적 · ⚠ 확인 안 됨
근거 · 없음
```

머리말은 `confidence: unconfirmed` 로 둔다.

그리고 **선택지를 제시해 물어본다.** 답을 받으면 채우고 `confirmed` 로 바꾼다.

```
왜 간단하게 만들고 싶으신가요?
  ○ 사용자가 이탈해서   ○ 개발이 복잡해서
  ○ 그냥 보기 안 좋아서 ○ 직접 입력
                          [나중에]
```

**"나중에"를 반드시 남긴다.** 매번 답을 강요하면 도구가 귀찮아지고, 귀찮으면 꺼버린다.

### 인용이 있어야 confirmed 다

`실제 목적`을 채우려면 **사용자가 실제로 한 말**이 근거에 있어야 한다.

```
근거 · 직전 대화에서 "가입하다 다 나가는 것 같다"고 언급    ← 인용 있음
근거 · 사용자가 이탈을 걱정하는 것으로 보임                  ← 인용 없음. 추론이다
```

인용할 게 없으면 `unconfirmed` 다.

## 되묻기 — 언제 물어보는가

매번 되물으면 흐름이 끊긴다. **네 가지에만 물어본다.**

| 되물을 때 | 그냥 넘어갈 때 |
|---|---|
| 의도가 두 가지 이상으로 해석됨 | 요청이 명확함 |
| 되돌리기 어려운 결정 | 사소한 수정 |
| 다른 팀원 결정과 충돌 | 이미 정한 것의 연장 |
| PRD 핵심 항목에 영향 | 실험적 시도 |

되묻기 발생률이 전체 요청의 15%를 넘으면 트리거가 넓은 것이다.

물어본 내용과 답은 `## 확인 질문`에 남긴다. **질문 자체가 기록의 일부다** — 나중에 "왜 이걸 물어봤지"가 판단 근거가 된다.

## 목차와 연결 (`links` · `orphan`)

기획 중반에 팀이 PRD 목차를 합의한다. 그때부터 로그가 항목에 붙는다.

```yaml
links: [PRD-3.2]        # 이 결정이 반영될 곳
```

이게 **기여 귀속의 재료**다. 기록 시점에 연결해두면, 나중에 AI 가 "이 문장은 누구 거지"를 추론할 필요가 없다.

### 목차에 없는 아이디어

```yaml
links: []
orphan: true
topic: "알림 기능"
```

**`orphan` 은 오류가 아니라 정상 상태다.** 목차를 정해놓고 그 안에서만 생각하면 발산이 죽는다.

같은 주제로 `orphan` 이 3건 넘게 쌓이면 알린다.

```
"알림" 관련 기록이 4건 쌓였습니다. 목차에 추가할까요?
```

목차는 확정이 아니라 초안이다. 갱신하면 `decisions/` 에 남긴다.

## 상태 바꾸기

```
논의중  ──→  결정됨     확정. links 연결 가능
   │
   ├────→  보류        판단 유예
   │
   └────→  폐기        철회. 삭제하지 않는다
```

**폐기해도 파일을 지우지 않는다.** "이건 안 하기로 했다"도 정보이고, 같은 아이디어가 다시 나올 때 근거가 된다. 대시보드에는 취소선으로 표시된다.

상태 변경 이력은 Git 이 자동으로 갖고 있다. 이게 발표물의 **「판단이 바뀐 지점」** 재료가 된다 — 발표에서 가장 잘 먹히는 대목인데 기억에서는 제일 먼저 사라진다.

`결정됨` 인데 `links` 도 `orphan` 도 없으면 추적이 끊긴다. 둘 중 하나는 있어야 한다.

## 검사

로그를 만든 직후에 돌린다.

```bash
scripts/validate_log.py members/<이름>/logs/
scripts/validate_log.py members/<이름>/logs/LOG-0012.md    # 한 건만
```

| 판정 | 뜻 |
|---|---|
| **실패** | 형식이 깨졌거나 **근거 없이 의도를 적었다**. 고쳐야 한다 |
| 확인 | 형식은 맞지만 다시 볼 만한 것 (사람 평가 표현, 인용 없는 confirmed 등) |

가장 중요한 실패는 이것이다.

```
실패  「실제 목적」을 적었는데 근거가 없습니다
      → 추측이면 비워두고 confidence 를 unconfirmed 로 두세요
```

**지침으로만 두면 까먹지만 검사가 있으면 못 지나간다.**

## 찾을 때 — 통째로 읽지 않는다

로그가 60건이면 전부 읽는 데 ≈24k 토큰이다. **필요한 것만 추린 뒤 그것만 읽는다.**

```bash
grep -l "topic: 로그인" members/*/logs/*.md        # 주제로
grep -l "links:.*PRD-3.2" members/*/logs/*.md      # 반영될 항목으로
grep -l "status: 논의중" members/*/logs/*.md       # 상태로
grep -rl "세션" members/*/logs/                     # 본문으로
```

**전수를 읽어야 하는 경우는 병합뿐이고, 그건 서브에이전트가 한다.**

그래서 `topic` 과 `files` 를 채우는 게 중요하다. 안 채우면 본문 검색밖에 못 하고, 본문 검색은 놓치는 게 많다.

## 자주 막히는 곳

| 상황 | 대응 |
|---|---|
| 결정인지 아닌지 애매함 | 위 4:4 기준으로 판단. 애매하면 남기지 않는다 |
| 사용자가 이유를 안 말함 | `실제 목적`을 `⚠ 확인 안 됨`, `근거`를 `없음` 으로. **추측 금지** |
| 되묻기에 "나중에" 답함 | `unconfirmed` 로 두고 진행. 나중에 채운다 |
| 목차가 아직 없음 | `orphan: true` 로 남긴다. 목차 합의 후 연결 |
| 한 대화에서 결정 3개 이상 | 각각 별도 로그. 하나에 몰아넣으면 기여 귀속이 안 된다 |
| 사용자가 기록 내용을 부정 | 즉시 고친다. 수정 이력은 Git 이 보존한다 |
| 이미 있는 결정을 다시 정함 | 새 로그를 만들고 `supersedes` 로 이전 것을 가리킨다 |
| 본문이 길어짐 (1200자 초과) | 길면 안 읽힌다. 결정과 근거만 남기고 줄인다 |
| 사람 이름 + 부정 표현 | 사람이 아니라 안(案)을 평가한다. "A안이 3.2 미충족" |
| 관련 로그를 찾아야 함 | **통째로 읽지 말고 `grep` 으로 추린다** |

더 많은 예외는 `troubleshooting.md` 에 있다.
